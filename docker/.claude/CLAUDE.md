# Agent Worker Rules

These rules apply to all Claude Code sessions in this container.

- **Branches and PRs via git + gh** — create a branch with `git checkout -b <branch>`, commit with explicit staging (see "Commit hygiene" below), push with `git push -u origin <branch>`, and open the PR with `gh pr create`. Never force-push (`--force`/`--force-with-lease`) unless explicitly told to by a human.
- **Never use `git stash`** — if you have uncommitted changes, commit them using the explicit staging pattern (see "Commit hygiene" below) before switching branches. Stashing loses track of changes.
- **PRs ready for review, never draft** — submit PRs without `--draft`, and if you resumed a branch whose PR is still a draft, promote it with `gh pr ready <number>` after submitting. PRs must not be left in draft.
- **Never work on main** — always create a branch first
- **Only assigned tickets** — never touch tickets assigned to others
- **Work document required before implementation** — every ticket MUST have a linked Linear document before any code is written. Use `create_document` / `update_document`, not comments. This is a hard gate enforced by the skill.
- **Document before commit** — update work document via `update_document` before every commit/push. Check off completed plan steps and update "Progress". Stale checkboxes waste future sessions.
- **Sync before push** — `git fetch origin`, then bring in the PR's base branch before every push: `git rebase origin/<base>` before the branch's first push, `git merge origin/<base>` once it's pushed (so no force-push is needed)
- **Sensitive file protection** — never stage `.env`, `*.key`, `*.pem`, credentials
- **Commit hygiene — never use `--all`** — `git commit -a` and `git add --all`/`-A`/`.` are forbidden. They sweep up untracked files (plugin injections, workspace debris, AGENTS.md) and produce commits that don't match what you edited. Instead: after each logical chunk, run `git -C /workspace status --porcelain`, verify the list matches files you intended to change, then stage each by name with `git add <path1> <path2>...`, and commit with `git commit -m "..."` (no `-a`). `.agents/`, `AGENTS.md`, `.claude/skills/` must never appear in a staged commit — they're injected at runtime.
- **Runtime-injected files are NOT your concern — never inspect or repair their git state** — `AGENTS.md`, `.agents/`, `.claude/skills/`, and `.claude/CLAUDE.md` are injected at container startup and deliberately set to `assume-unchanged` and/or excluded. They will therefore appear in *odd* git states — showing as modified, untracked, or stubbornly "unchanged." **This is by design, not a problem to solve.** Do NOT investigate it: no `git status`/`ls-files`/`diff`/`checkout`/`update-index`/`git stash` aimed at these paths to work out why they look that way. Just ignore them — they are never something you stage, fix, refresh, or reason about. (Chasing their git state is a known time-sink: don't.)
- **Post-push verification — mandatory** — after every push, run `git -C /workspace diff --stat origin/<base-branch>...HEAD` and confirm **every file you edited this session appears in the branch diff**. Your "edited this session" list is the set of paths you passed to Edit, Write, or NotebookEdit during this run — track this as you work. Other files in the diff are fine (prior sessions on this branch may have committed them already). If **any file you edited this session is missing from the pushed branch**, STOP: call `reply({ text: "Push verification failed — edited <paths> this session, but the pushed branch does not contain <missing paths>", type: "blocker" })`, then `post_status({ status: "waiting_for_feedback", message: "Push verification failed" })`. Do NOT call `post_status({ status: "complete" })` — the push did not capture your work.
- **Never re-flag dismissed review issues** — check prior reviews and work document Review Notes before posting
- **Never re-request review from approvers** — only re-request when state is CHANGES_REQUESTED or COMMENTED
- **Channel for all human interaction** — use the channel tools instead of AskUserQuestion: `reply` (blocks until the human answers — questions, approvals, blockers only) and `say` (posts to the thread and returns immediately — acknowledgements, FYI reports, progress notes). Never use `reply` for a message you don't need answered: it parks you waiting for an answer that never comes.
- **Raw text output reaches NOBODY** — in headless mode, text output goes to the log stream, not to a human. Anything you intend for the human MUST go through `reply` or `say`. Never output questions, prompts, or "would you like..." text without a `reply()` call. This applies with full force MID-CONVERSATION: when a `reply` call returns the human's answer and you want to respond to it, that response MUST go through the channel — `reply` if you need another answer, `say` if it's just an acknowledgement (e.g. "got it — proceeding"). Answering in plain text and then completing strands your answer in the log stream, invisible to the human. Never `post_status complete` right after the human asked you something.
- **Status updates** — use `post_status` tool to keep dashboard current
- **No worktrees by default** — the container is the isolation; work directly in `/workspace`.
- **Ending your turn ends the process — "waiting" kills you** — this is a one-shot headless run (`claude -p`). The moment you stop calling tools, the process exits and the container is torn down. There are NO wakeups, NO background-task notifications, NO resuming later: `ScheduleWakeup` is not available, and phrases like "I'll pause here and wait for the install to finish" are fatal — the install keeps running for a few seconds inside a dying container and all uncommitted work is lost. To wait on a long command, BLOCK on it in the foreground: run it directly in Bash with a large `timeout` parameter (up to 10 minutes), e.g. `pnpm install 2>&1 | tail -20`. If it exceeds the timeout, run the same command again — package managers resume incrementally. Never `nohup`/`&` a command and then end your turn expecting to come back.
- **Dependencies are pre-installed at startup** — for pnpm repos, the container entrypoint runs `pnpm install --frozen-lockfile --prefer-offline` (against a shared package store) before your session starts, so `node_modules` already exists. Do NOT re-run install before lint/typecheck — just run the checks. Only if `/workspace/.agent-install-failed` exists, or a command fails with missing-module errors, run `pnpm install` yourself once, in the foreground (see rule above; the shared store makes it much faster than a cold install). If that fails or still hasn't completed after two foreground attempts, skip testing and note the blocker via `reply` — do not retry repeatedly, and never end your turn to "wait for it".
- **Run static checks locally; leave the test suite to CI** — before pushing, type-check and lint the code you touched (see the repo's own docs for the exact commands). These are cheap now that dependencies are pre-installed, and they catch the failures that otherwise cost a full CI round-trip plus a fix-ci dispatch. Do NOT run the full test suite locally unless the task specifically requires it — the complete suite belongs to CI.
- **Manual steps awareness** — always scan plans for steps requiring human action, flag them, and remind after implementation
- **Save useful discoveries** — when you learn something non-obvious about the repo (build quirks, patterns, error solutions), save it with `save_memory` so future agents benefit

## Stacked-PR CI: merge-base drift

Symptom: CI fails on a stacked PR (one whose base is another PR's branch) with build/type errors that reference symbols which *do* exist in the parent branch's current tip.

Cause: GitHub's CI merge ref (`refs/pull/<N>/merge`) was computed when the parent branch was at an older commit, and nothing has been pushed to this PR since the parent changed.

Diagnose:
1. `git -C /workspace fetch origin "pull/<PR_NUMBER>/merge"`
2. `git -C /workspace log -1 FETCH_HEAD` — read the "Merge X into Y" line
3. Compare `Y` against `git -C /workspace rev-parse origin/<parent-branch>`. If they differ, it's merge-base drift.

Fix: push new content to the PR head — that forces GitHub to recompute `refs/pull/<N>/merge`. If you have no real change to make, add a trivial edit (a comment, a newline) to a file already in your diff, stage explicitly, commit, and push. Do NOT force-push to work around it.

Verify: after the push, `git fetch origin pull/<N>/merge` again and confirm the "Merge X into Y" line now references the current parent tip.
